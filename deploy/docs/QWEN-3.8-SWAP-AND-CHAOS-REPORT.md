# Overnight chaos-test + Qwen 3.8 readiness report
_Generated by Claude during the pre-3.8 hardening run (2026-08-12, overnight)._

## TL;DR
Chaos-tested the local-LLM gateway stack and fixed **4 real issues** before the Qwen 3.8 drop-in. The gateway now fails over cleanly from every backend failure mode I could inject, and the 3.8 swap has one nasty landmine removed and a documented procedure below.

## Bugs found & fixed (all live)
1. **Watchdog hardcoded `qwen3.6:27b`** → after a model swap it would probe a now-404 model, read that as the "alive-but-not-generating" wedge signature, and **false-positive restart-loop the engine.** FIXED: `vllm-watchdog.sh` now auto-discovers the served model from `/v1/models` (falls back to the old name). Swap-safe.
2. **Wedged backend hung the gateway.** If local accepts the connection but never emits a token (a real wedge, or headers-then-silence), the gateway hung up to ~10 min instead of failing over. FIXED: added an **adaptive first-token timeout** in `keepalive-shim.py` (`SHIM_FIRST_TOKEN_BASE=15s + est_prompt_tokens/500`) — a wedge fails over to DeepSeek in ~15s, while a legit big-context prefill still gets the minutes it needs. Verified with a mock wedge (16s failover).
3. **budget=1 was overflowing ALL big requests to DeepSeek** (needless cost). A "big" request counted as 2 units and `2 > budget(1)`. FIXED: a big request now occupies the *whole current budget* (`effective_budget()`), so a single big request runs LOCAL (safe) and only concurrent work overflows. Verified: a 33K-token request served local, no OOM.
4. **The recurring EngineCore OOM** (what you kept hitting): with 12 extensions, each pi turn fires multiple LLM calls that overlapped 2-wide on the GPU and OOM'd. FIXED earlier by **budget=1** (never 2 concurrent local). Verified by reproducing your exact "Do you have GitHub MCP setup?" turn end-to-end — completes clean; and a 12-concurrent burst → 1 local + 11 DeepSeek, 0 OOM.

## Regression caught & fixed overnight (proof the monitoring works)
- **02:58 — a solo OOM crash** (NRestarts 5→6). Diagnosed: budget=1 was respected (never 2 concurrent local), so this was a **single request too big for the box** (large context + long generation peaked past the ~36 MiB free VRAM). It self-recovered, but would recur.
- **Fix (5th bug):** added `SHIM_MAX_LOCAL_TOKENS=80000` — requests whose est. `prompt + max_tokens` exceed the cap route straight to DeepSeek instead of OOMing local. Verified: ~83K-token request → DeepSeek, ~44K → local, engine healthy. budget=1 stops concurrent-OOM; the cap stops single-too-big-OOM. Tune up if it overflows too much.

## ⭐ Qwen 3.8 27B drop-in procedure (do this when weights land)
1. Put the 3.8 weights somewhere (e.g. `~/Desktop/models/Qwen3.8-27B-<quant>`), self-quantize/AWQ per the `qwen-3.8-watch` note if needed.
2. Edit `~/.local/share/vllm-qwen27b/serve-tqk8v4-fg.sh` (back it up first):
   - `--model` → the 3.8 path.
   - `--served-model-name` → add the 3.8 id(s). **Recommended: keep a STABLE alias** (e.g. add `qwen-local`) so clients never need updating again. If you keep `qwen3.6:27b` in the list too, nothing breaks during transition.
3. `sudo systemctl restart vllm-qwen27b` (gateway overflows to DeepSeek during the ~2-min reload — no outage).
4. Update **pi's model** on the VM (`~/.pi/agent/models.json`, provider `local`) to the new served id (or `qwen-local` if you added the alias). Same for `subagents`/agent defs if they pin an id.
5. Verify: `curl -s localhost:8000/v1/models` shows the new id; send a test chat. The watchdog auto-adapts (no change needed).
6. Things that still hardcode `qwen3.6:27b` and would need the new id (or the stable alias): pi `models.json`, and any Applicant/Hermes/AZ configs pointing at `:8000`. The gateway + watchdog do NOT.
